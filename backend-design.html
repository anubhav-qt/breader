Backend & infrastructure

Design v0.3 · 26 September 2026 · Phase 1 built and its gaps closed, not yet deployed (§15)

Breader keeps working when your laptop is off, and a laptop going down never loses a change. Every write is saved in Supabase first. Your laptop keeps a live copy, answers the app’s requests and does the heavy work. A free server on Render takes over while the laptop sleeps. It all runs on free tiers.

Requirements

What it does

  • Opens a library with a key or a login, on any browser.
  • Works offline: add books, read, take notes. Changes sync when the connection returns.
  • Stores book files, covers and note images.
  • Syncs reading places, card edits (name, colour, favourite), reader settings, highlights and notebooks.
  • Lets a logged-in reader claim a key library into their account.
  • Runs a public shelf with categories, tags, search, reports and takedowns.
  • Runs circles: invite links, shared books, per-reader progress.
  • Answers AI requests from a free daily quota. Readers with their own key call the provider from the browser.

How well it does it

  • Cost: $0 a month. The one unavoidable cost is a domain name (about $10 a year).
  • No lost changes: a laptop that loses power, sleeps or is closed mid-write loses nothing.
  • Availability: the app keeps working while the laptop is off, with a switch-over of a few seconds.
  • Speed: most requests under 150 ms from India. Reading never waits on the network, because the book is in the browser.
  • Scale: comfortable to about 3,000 libraries and 300 readers a day on free tiers. §13 shows what runs out first.
  • Portability: the same container image runs on the laptop, on Render, or anywhere else later.

Architecture

Where data lives

You asked for the data on your laptop and in Supabase, with both updated on every change. This design does that, and fixes the order. A write counts as saved only once Supabase has it. Your laptop copies it a few seconds later.

The order matters because a laptop can shut down in the middle of a write. Anything saved only on the laptop would be lost with it, or would have to be merged by hand later. With Supabase first, the fallback server always has everything, and a returning laptop simply catches up.

The pieces

PieceRuns onJob
AppCloudflare PagesThe current React frontend, built and served as static files. It never depends on the laptop.

mirror PostgresLaptopA full copy of the database a few seconds behind. It serves shelf browsing, search and circle listings, and holds data that can be rebuilt (search index, later AI embeddings).

FilesCloudflare R2Book files, covers, note images, backups. The laptop keeps a copy of every file.

How the laptop copy stays current

Postgres replication would be the obvious tool, but Supabase’s free plan only offers the direct connection it needs over IPv6. A replication slot would also hold back Supabase’s disk while the laptop sleeps. A small change feed avoids both problems:

  1. A trigger on each table writes the changed row into change_log in the same transaction, tagged with the transaction id.
  2. The worker reads changes after its cursor, but only from transactions that have finished. It reads below the oldest transaction still running (pg_snapshot_xmin), so a slow transaction is never skipped.
  3. Every row carries a version number. The mirror applies a change only when it’s newer than what it has, so replays and repeats do no harm.
  4. It polls every 2 seconds while changes are arriving and backs off to 30 seconds when quiet. After more than 14 days away, the laptop reloads the whole database, which is small.

The API reads a reader’s own library from Supabase, so they always see their own writes. Browsing reads come from the mirror. That split also keeps Supabase inside its 5 GB a month of free egress.

Failover

Only the API moves between hosts. The app, the files and the database stay where they are, so a switch never has to move data.

Laptop on

The browser talks to the laptop. Writes go to Supabase, and the laptop copies them back within seconds.

Laptop off

Requests to api. fail, so the app moves to fb. in about 4 seconds. The fallback reads and writes Supabase directly.

Laptop back

The app checks api. every minute and moves back when it answers. The change feed replays whatever the laptop missed.

Supabase down (rare)

Nobody can save to the server. The laptop serves the shelf read-only from its copy, and every browser keeps its changes in the outbox until Supabase is back.

How the app switches

  • The app knows two API addresses, api. and fb., and sends each request to whichever is current.
  • A network error, a 4-second timeout, or a 502, 503, 504 or 530 from Cloudflare (530 means the tunnel has no laptop behind it) marks api. as down. The request is retried once on fb., which is safe because every write carries an id and applies only once.
  • The session cookie is set on the parent domain and signed with a secret both servers share, so either accepts it. A key session names the library and the key’s epoch; replacing a key raises the epoch, which ends every session opened with the old one. Account sessions (Phase 2) live in Postgres, which both servers read.
  • Render’s free tier sleeps after 15 minutes idle and takes about a minute to wake. An uptime check every 5 minutes keeps it awake, so a switch takes seconds. That uses 744 of Render’s 750 free hours a month.
  • While the laptop is off, jobs wait in the queue. Sign-up and password emails are sent within the request itself, so they still work. AI works on both servers.

Identity & keys

There are two kinds of identity. A library is what a key opens: books, reading places, highlights, notebooks and circle memberships all belong to it. An account is a person who has logged in. An account owns exactly one library. Only accounts can share on the public shelf or use the free AI quota, so every public book has a person behind it, and minting new keys can’t get around a limit.

The flows

  1. First book, no login. The browser creates a library id and a key (it does this today: BRDR- plus 20 Crockford characters, 100 bits). It keeps the book in IndexedDB and shows the key once, in your words: “Your personal key. Store it somewhere safe, it can’t be recovered. Log in to keep your books with your account, or use this key.” All of this works offline.
  2. Registering. When the browser is online, the app registers the library with POST /v1/libraries. The server stores only an HMAC of the key, never the key itself. The book uploads in the background.
  3. Another browser. The reader types the key into the Key dialog. The server looks up the HMAC, sets a session cookie for that library, and the app pulls everything down.
  4. Logging in later. If this browser holds a key library, the app offers “Keep these books in your account”. The claim moves books, reading places, highlights and notebooks into the account’s library in one transaction, then retires the old key.
  5. A new account gets a library and a key of its own. The Key dialog shows that key, with options to replace it or switch key access off.

Sync

The browser stays the first place anything is saved, as it is today. The server becomes the place where browsers meet. Every change the app makes (open a book, move the reading place, rename a card, highlight, write a note) is written to an outbox in IndexedDB first, so the app never waits for the network.

  1. Push. POST /v1/sync/push sends the outbox with the client id and a mutation id on each change. It runs 3 seconds after the last change (at most 20 seconds after the first), when the tab is hidden, and when the connection returns. The server applies the batch in one transaction, raises the library’s rev and stamps every changed row with it. A retry of the same mutation id does nothing.
  2. Pull. GET /v1/sync/pull?since=<rev> returns every row with a higher rev, tombstones included, and the new rev. It runs when the app opens, on focus, after a push, and every 2 minutes while open.
  3. Why pulls never miss a change. The library row is locked during a push, so revs rise in the same order the changes were saved.
  4. Several tabs. Every tab of a browser shares one outbox. Tabs change the library and the outbox only under one Web Lock, always on what’s stored rather than on their own earlier copy, and tell each other through a BroadcastChannel so the others reload. One tab at a time talks to the server.
  5. After a restore. The database carries a sync timeline, and a restore gives it a new one. A browser that sees a new timeline, or a rev lower than one it pulled, sends everything it holds again (books, places, edits, removals, and files the server no longer knows) before it takes anything from the server.
  6. Shared data. Circles have their own rev and pull the same way. The public shelf is fetched page by page and cached at the edge for 60 seconds.

When two devices disagree

Files

Book bytes never pass through the API. A home connection uploads slowly, and R2 charges nothing for downloads.

Adding a book

  1. While the reader chooses private or shared, the browser computes the file’s SHA-256.
  2. POST /v1/uploads with the hash, size and type. The server checks the quota and the blocked list. If the same file is already in this library or on the public shelf, it links to that copy and skips the upload.
  3. Otherwise it returns a signed R2 upload link that lasts 15 minutes and accepts only that size.
  4. The browser uploads directly to R2.
  5. POST /v1/uploads/{id}/complete. The server checks the stored size and checksum, marks the file ready and counts it against the quota.
  6. The worker copies the file to the laptop. For shelf books, it also checks that the file opens.
  • Reading a book: GET /v1/files/{id} checks access and redirects to a signed R2 link valid for 10 minutes. The browser keeps a copy in IndexedDB.
  • Covers of shelf books are public and cached at the edge. Private covers use signed links like books.
  • Storing each file once only happens within a library and against public books. A stranger therefore can’t test whether someone else holds a private file.
  • Quota counts every file a library uses, even when the bytes are shared with others.
  • Clean-up: a file no book points at is deleted after 7 days, and its space goes back to the library. Removed books still point at theirs until their tombstone is purged, so Undo brings a book back whole. An upload link never finished is dropped after a day.

Shelf & circles

The public shelf

  • Sharing needs a login with a verified email. The reader picks one category from the curated list, adds up to 5 free tags, and ticks “I have the right to share this book”.
  • The entry keeps a copy of the title, author, colour and cover, so the shelf draws without extra lookups.
  • Browse by category or tag, or search by title, author and tag. Search uses Postgres full-text matching, plus trigram matching for typos. Results come from the laptop’s copy and are cached at the edge.
  • Everyone who opens a shelf book keeps their own reading place, highlights and notes in their own library.
  • The sharer or an admin can take a book off the shelf.

Moderation

  • A Report button sends the book to the admin queue.
  • A takedown hides the entry and blocks the file’s hash from being shared publicly again.
  • A terms page gives a copyright contact address. Once strangers can share, copyrighted books will turn up, and a working takedown process is what keeps the shelf allowed to exist.

Circles

  • Anyone with a library, key or login, can create a circle and share an invite link: /c/<token>.
  • Tokens are random and stored hashed. The owner can revoke them or set them to expire.
  • Every member can add books and read every book in the circle. The member who added a book, or the owner, can remove it.
  • A circle has its own rev, so members pull circle changes the same way they pull their library.
  • For later: highlights and notes visible to the circle, for study groups. The notebook model can take a visibility setting without changes.

Study notes

In study mode the page sits on the right and a scratchpad on the left. The backend sees one notebook per reader per book. The notebook holds a general note and any number of anchored notes: a page note, a topic note tied to a chapter in the table of contents, or a passage note tied to a highlight.

Scratchpad contentHow it’s stored
Text and markdownRich text inside the notebook’s Yjs document (TipTap on ProseMirror in the browser).
Drawings and sketchesVector strokes (points, pressure, colour) in the same document. Strokes are smoothed before saving to keep them small.
Images and page snipsThe browser crops the rendered page to a WebP image and sends it through the upload flow in §7. The note stores a reference to the attachment.
Quotes linked to the bookA link to a highlight’s anchor. Clicking it opens the book at that passage.
  • Anchors use the reader’s existing position (section, block, offset) plus the quoted text and a few words either side. If the book file changes, the passage can still be found by its text, the way the W3C web annotation standard does it. PDF anchors use the page and text offsets.
  • Storage: recent edits are kept in Postgres and folded into a snapshot in R2 every 50 updates or when the notebook goes quiet. That stops large drawings from filling Supabase’s 500 MB.
  • Offline editing works like everything else: edits go to the outbox and Yjs merges them.

AI

The book is already parsed and in the browser, so the browser builds each prompt’s context: the selection, the pages around it, the reader’s notes, and passages found by searching the book locally. So in v1 the server needs no copy of the text, and AI works on the fallback server too.

Free quota

  1. The browser sends the task and its context to POST /v1/ai/{task}.
  2. The gateway checks the login and the day’s quota (25 requests to start).
  3. It picks a key from the pool. Keys that hit a rate limit rest for a while.
  4. It streams the answer back and records the tokens used.

Bring your own key

  1. The reader pastes their own key into settings. It stays in that browser.
  2. The browser calls the provider directly, with the same prompt code as the gateway.
  3. Neither the key nor the text reaches Breader’s server.

First tasks

  • Explain or define the selected passage.
  • Story so far: a recap built only from the text before the reader’s place, so it can’t spoil anything ahead.
  • Ask the book a question.
  • Study: turn my notes into flashcards, or quiz me on this chapter.

The free quota runs on a small, fast model (for example Claude Haiku 4.5). Readers who bring a key choose their own model. The key pool is a list in the server’s settings, so moving to a single paid account later changes one setting. Rotating keys from several accounts to stretch free tiers usually breaks the providers’ terms, and a provider can ban every linked account at once, so treat that as a short-term bridge.

Later, the laptop can pull out the text of shelf and circle books and build embeddings in its copy of the database (pgvector), for questions across a whole library.

The laptop

Docker Compose runs on Docker Desktop (installed now), OrbStack or Colima. Every container restarts on its own after a reboot or crash. The full file is infra/compose.yml, and infra/README.md walks through setting up every account. In short:

services:
  mirror:   pgvector/pgvector:pg17          the copy; no ports published
  migrate:  node dist/migrate.js            Supabase and the copy, then exits
  api:      node dist/api.js   ROLE=laptop  after migrate; transaction pooler
  worker:   node dist/worker.js             after migrate; session pooler, TZ=Asia/Kolkata
  tunnel:   cloudflared tunnel run          api.breader.example → http://api:8787
  • Database connections: the API uses Supabase’s transaction pooler and the worker uses the session pooler. Both work over IPv4.
  • Staying awake: in System Settings › Battery › Options, turn on “Prevent automatic sleeping on power adapter when the display is off”. With the lid closed, a Mac sleeps unless an external display is attached. Sleep is harmless anyway, because the fallback takes over.
  • FileVault must be on. The laptop holds a copy of everyone’s private books.

Shipping a change

  1. Push to main. GitHub Actions runs type checks, lint and tests.
  2. It builds one image for both arm64 (the Mac) and amd64 (Render) and pushes it to GHCR.
  3. A CI job applies new migrations to Supabase. On the laptop, a one-shot migrate container brings Supabase and the copy up to date before the new api and worker start. A database lock makes the two migrators take turns.
  4. Render deploys the new image from a deploy hook. The laptop pulls it with infra/update.sh, which launchd runs every 5 minutes. It restarts the stack only when the running API is on an older image, so a stack you stopped stays stopped.
  5. Cloudflare Pages builds the app from the same commit.

For a few minutes the laptop and Render can run different versions, so migrations only ever add. A column is added in one release and removed in a later one, once no running code uses it.

Backups and recovery

Supabase’s free plan keeps no backups, so the laptop copy becomes the backup. Every night at 03:00 IST the worker dumps the laptop copy, which costs no Supabase egress. It encrypts the dump with age, keeps 14 days on the laptop and puts 7 daily and 4 weekly copies in a separate R2 bucket. Every four weeks, after that night’s backup, the worker restores a dump of the copy into a scratch database, checks every table row for row, and checks that the night’s backup reached R2 whole. It can’t decrypt its own backups, because the key isn’t on the laptop, so opening one with the key stays a manual drill in infra/README.md, a few times a year. A restore also runs migrate, which moves the version sequence past the restored rows (the copy never advances it, and new writes would otherwise look older than old ones) and starts a new sync timeline (§6).

Watching it

  • Uptime checks on api., fb. (this check also keeps Render awake) and the app. Alerts go to email or Telegram.
  • A heartbeat from the worker every 5 minutes, sent only while the copy is under 60 seconds behind, so one silence alert (after 10 minutes) covers a stopped worker, a sleeping laptop and a stuck copy. UptimeRobot’s heartbeats are paid; Healthchecks.io’s free plan has them.
  • Sentry for errors in the app, the API and the worker. A small reporter sends only the error and its stack, each error at most once every 10 minutes, so the free plan lasts.
  • A status page on each server (/admin, behind an admin token) shows which server answered, the copy’s lag, the change feed, Supabase’s size, files in R2, libraries about to expire, and when each worker job last worked or failed. Emails and the AI key pool join it when they exist. Supabase shows egress only in its own dashboard.
  • The change feed’s constant polling should keep Supabase from counting the project as idle and pausing it. The status page shows when the laptop last read the feed.

Security

  • No ports are open on the laptop. The database copy is reachable only inside Docker’s network.
  • Turn off Supabase’s Data API, or keep the tables in a schema it doesn’t expose. Only Breader’s servers talk to the database.
  • Keys are 100 random bits. The server stores an HMAC-SHA256 of each key with a secret pepper that the laptop and Render share. Keys travel only in request bodies over HTTPS, never in URLs.
  • Sessions use a cookie that’s HttpOnly, Secure and SameSite=Lax, set on the parent domain. Writes also check the Origin header.
  • Rate limits, per address and counted by each server on its own: opening a key 10 times a minute, registering a library 10 times an hour, and asking to upload 60 times an hour. These are looser than first planned, because Indian mobile carriers put many readers behind one address. Each server reads the address only from cf-connecting-ip, which Cloudflare writes itself in front of both (the tunnel, and Render’s edge), so a request can’t choose its own. Render’s last x-forwarded-for entry is its internal proxy, not the reader. Cloudflare Turnstile joins sign-up and key registration in Phase 2.
  • Upload size is limited in the signed link and checked again afterwards. EPUB HTML is always cleaned in the browser before display, as DOMPurify already does. Files are served from R2 or files., never from the app’s address.
  • Secrets live in .env on the laptop (readable only by you, never committed), in Render’s environment settings and in GitHub secrets.
  • Accounts can be deleted and exported, as India’s data protection law (DPDP Act) expects.

What to do as limits approach

  • R2 at 10 GB: R2 charges $0.015 per GB a month beyond that, so 50 GB costs about $0.60 a month. This will be the first bill. The free alternatives are tighter quotas, or adding Backblaze B2’s 10 GB free tier as a second bucket.
  • Supabase database or egress: move more reads to the laptop, trim the change log sooner, or move to Supabase Pro ($25 a month) or another Postgres. The schema is plain Postgres, so moving is a dump and a restore.
  • A laptop that’s often off: add an always-on free VM (Oracle Cloud Always Free has Mumbai and Hyderabad regions) that runs the worker as well as the API.
  • AI spending: switch the key pool to a single paid account.

Phase 1 as built

Foundation runs locally on the image production will use, with Postgres and RustFS standing in for Supabase and R2. It was tried end to end with two browsers:

  • A book added in one browser registered its library, uploaded straight to storage, and reached Supabase, the laptop’s copy and the laptop’s file store. A second browser opened the library with the key, typed carelessly, and downloaded the book through a signed link. Reading places synced back.
  • Stopping the laptop’s API moved the app to the fallback within one request; starting it again moved the app back within a minute.
  • A nightly backup decrypted and restored. Restoring the copy into a fresh Postgres, then running migrate, repaired the version sequence.
  • Two tabs in Chrome edited one library at once, and every edit reached the server and both tabs. Then the server was put back to an older state with a new timeline, and the browser sent its edits and a lost book again, taking the book’s file back from storage without uploading it. A purged removal and a wholly lost library came back right too.
  • The nightly backup, the restore test and clean-up ran in the worker image and logged themselves to the status page.
  • 48 server tests cover keys and sessions, the sync rules, uploads, the change feed, clean-up, restores, the restore test, the R2 check and the status page. CI runs them on every push to dev and on pull requests.
